# 多平台電商對帳引擎

把電商賣家每月的手動對帳，從逐筆核對壓縮成一次上傳。
核心是可插拔的帳單解析層與三階段匹配演算法。

> **目前狀態：v0.2 — 開發中。**
> 領域層（`Money`、領域模型、正規化）已完成並通過測試；
> 解析層、對帳引擎、API 與前端依序開發中，進度見下方路線圖。
> v1 的 CLI + Excel 版本保留在 [`legacy/`](legacy/)，作為演進的紀錄。

---

## 問題

電商賣家在多個平台銷售，每個平台每月寄來一份結算單。賣家需要確認：
平台撥的錢，跟自己系統裡的訂單對得起來嗎？

實務上這件事很難自動化，因為兩邊的資料對不上的方式有很多種：

- 訂單編號格式不同（平台在結算單上加了前綴、大小寫不一致、混入全形字元）
- 金額有差（費率調整、運費補貼、部分退款）
- 有些結算列根本沒有訂單編號（平台端的調整與沖銷）
- 跨月結算讓日期錯開
- 每個平台的檔案格式、編碼、表頭結構都不一樣

所以這不是一句 SQL JOIN 能解決的問題。

## 做法

```
自有訂單 ─┐
          ├─→ 正規化 ─→ Stage 1 精確匹配 ─→ Stage 2 容差匹配 ─→ Stage 3 模糊匹配 ─→ 四象限報告
平台結算單 ┘                (編號＋金額全等)    (編號同、金額異)     (候選集評分)
```

| 階段 | 條件 | 處理 |
|------|------|------|
| Stage 1 精確 | 正規化後編號與金額皆相符 | 自動勾稽 |
| Stage 2 容差 | 編號相符、金額有差 | 計算差額並歸因（費率／運費／退款／捨入） |
| Stage 3 模糊 | 編號缺失或異常 | 以日期窗口＋金額分桶建候選集，加權評分後進人工確認佇列 |

輸出分為四個象限：**已勾稽**、**金額差異**、**漏記單**（平台有我方無）、
**未撥款**（我方有平台無）。

Stage 3 的關鍵在於先縮小候選集再評分：用日期窗口與金額分桶建索引，
讓每筆未匹配記錄只跟少數候選比對，複雜度從 O(n²) 降到近似 O(n·k)。

## 架構

```
src/reconciliation/
├── domain/          純 Python，零框架依賴。Money、領域模型、匹配演算法
├── parsers/         BaseSettlementParser ＋ 各平台實作 ＋ 註冊表
├── repositories/    介面 ＋ SQLAlchemy 實作
├── services/        使用案例編排，交易邊界
└── api/             FastAPI routers，只處理 HTTP
```

只有一條硬規則：**`domain/` 不 import 任何框架**。
沒有 FastAPI、沒有 SQLAlchemy、沒有 pandas、沒有 openpyxl。
因此領域層的測試不需要資料庫，跑完一輪不到 0.2 秒。

`repositories/` 這一層存在的唯一理由，是讓 SQLite 換成 PostgreSQL
只需要改連線字串——因為沒有任何一行原生 SQL。

## 幾個刻意的設計決策

**金額不用 `float`。** `Money` 值物件以最小貨幣單位的整數儲存，
捨入策略明確指定為 ROUND_HALF_UP。這是從 v1 的 float 實作改過來的，
理由與代價寫在 [ADR 0001](docs/adr/0001-money-as-integer-minor-units.md)。

**非法狀態不可表示。** `MatchResult.__post_init__` 讓「MATCHED 卻沒有 order」
這種狀態根本無法被建構出來。與其在下游到處寫防禦性檢查，不如在型別層擋掉。

**正規化只用於比對，不改寫原始資料。** `Order.external_order_id` 保存平台
實際印出來的字串，正規化只發生在匹配當下——人工查核時必須看得到原文。

**缺失的訂單編號回傳 `None`，不是空字串。** 如果都正規化成 `""`，
缺編號的記錄會在 Stage 1 互相匹配上，產生大量假的對帳結果。

## 關於資料

本專案使用**合成資料**。作者手上沒有真實的平台結算單，
因此 `scripts/gen_fixtures.py`（W2）會依據公開的結算單欄位結構產生測試資料，
並刻意注入真實情境會出現的髒資料：重複列、缺失訂單編號、金額不符、
退款列、跨月結算、編碼與日期格式差異。

這一點在此明確說明，不做任何有真實資料的暗示。
