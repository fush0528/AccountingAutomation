# 小樣本說明

這組資料的每一列都是為了示範某一種對帳情況。**這是合成資料**——
作者手上沒有真實的結算單，所有金額與編號都是產生的。
欄位規格則取自公開技術文件，出處見
[ADR 0005](../../docs/adr/0005-sample-data-provenance.md)。

由 `python scripts/gen_samples.py` 產生，內容固定不會變動。

> **這組資料的自動化率沒有參考價值。**
>
> 12 筆訂單裡刻意塞滿了各種例外，所以 Stage 1 只佔 28.6%。
> 真實情況下絕大多數交易是單純相符的——`gen_fixtures.py` 產生的
> 300 筆資料比例才接近現實，自動化率 79.6%。
>
> 這一組的用途是**逐列講解**，不是量測效能。兩者不要混用。

## 檔案

| 檔案 | 現實中誰給的 | 格式 | 主要難點 |
|---|---|---|---|
| `orders.csv` | 我方自己的系統 | UTF-8 CSV | 對帳的另一半，不是上傳的對象 |
| `platform_a_sample.csv` | **第三方金流商**的撥款對帳檔 | UTF-8 CSV | 手續費拆成三欄要相加；退款寫在銷售列的欄位裡；檔案自帶淨額欄可交叉驗證 |
| `platform_b_sample.xlsx` | **電商平台**賣家後台匯出的報表 | Excel | 報表標題 ＋ 兩層表頭 ＋ 合併儲存格，表頭列號要用找的；金額是數值型 |
| `platform_c_sample.csv` | **舊 ERP／供應商**的對帳單 | **Big5** CSV | 民國年日期；金額有千分位且是字串；退貨列印正數要自己轉負 |

三個平台的欄位名稱、日期格式、編碼、數字寫法、甚至「退款」的表示法
全都不同，但解析出來都是同一種 `SettlementRecord`。

特別值得看的是退款：平台 A 把它放在銷售列的一個欄位，平台 C 另起一列。
同一件商業事實、兩種表示法——parser 把它們都收斂成「一筆銷售記錄 ＋
一筆退款記錄」，所以下游的歸因邏輯完全不需要知道資料來自哪個平台。

## 結算單上的每一列

| 結算單上的編號 | 這一列的特色 | 預期的對帳結果 |
|---|---|---|
| `SP-A1B2C3D4` | 編號、金額完全相符 | Stage 1 精確匹配 → 已勾稽 |
| `SP-A2B3C4D5` | 手續費比我方預期多 40 元 | Stage 2 容差匹配 → 金額差異，歸因「費率調整」 |
| `SP-A3B4C5D6` | 銷售列 | 與下一列合併成同一筆結論 |
| `SP-A3B4C5D6` | 退款寫在銷售列的「退款金額」欄，不另起一列 | 同一列拆成兩筆記錄 → 歸因「部分退款」 |
| `SP-A4B5C6D7` | 與下一列一模一樣（平台重複匯出） | 第二次出現會被 fingerprint 擋下 |
| `MO-B1C2D3E4` | 編號被寫成小寫 | 正規化後 Stage 1 仍然命中 |
| `MO-B2C3D4E5` | 訂單金額比我方多 60 元（運費補貼） | Stage 2 → 歸因「運費補貼或折扣」 |
| `MO-B3C4D5E6` | 訂單編號欄是空的 | Stage 3 模糊匹配靠金額＋日期＋商品名稱救回 |
| `MO-ZZZZ9999` | 我方查無此訂單編號 | → 漏記單（平台有、我方無） |
| `PC-C1D2E3F4` | 編號是全形字元 | NFKC 正規化後 Stage 1 命中 |
| `PC-C2D3E4F5` | 手續費差 0.5 元 | Stage 2 → 歸因「捨入誤差」，可忽略 |
| `PC-C3D4E5F6` | 編號空白，金額差 90 元、商品名稱也對不上 | Stage 3 分數不足 → 漏記單，但附上候選與理由 |
| `PC-C4D5E6F7` | 銷售列 | 與下一列合併 |
| `PC-C4D5E6F7` | 全額退款列 | 淨撥款為 0 → 歸因「部分退款」 |

## 怎麼用

```bash
python scripts/serve.py            # 啟動網頁介面
# 在「上傳」頁把三個 platform_*_sample 檔案傳上去
# 同一份再傳一次，看 was_duplicate 變成 true
# 到「總覽」頁按開始對帳，再到「明細」頁逐列對照上表
```

資料小到可以在 Excel 裡打開逐列看完——這正是它跟
`gen_fixtures.py` 產生的幾百筆統計資料的差別。
