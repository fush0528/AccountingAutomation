# ADR 0002：對帳採三階段匹配，而不是單一匹配規則

- 狀態：已採用
- 日期：2026-09-17
- 相關：[ADR 0001](0001-money-as-integer-minor-units.md)（金額相等性是 Stage 1 的前提）

## 背景

對帳要回答的問題是「平台撥的錢，跟我方的訂單對得起來嗎」。
最直覺的實作是拿訂單編號做一次 join：

```python
by_id = {o.external_order_id: o for o in orders}
for record in records:
    order = by_id.get(record.external_order_id)   # 對得到就勾稽
```

這在合成的乾淨資料上可以跑出很漂亮的數字，但它對真實結算單的三個事實視而不見：

1. **編號不會剛好相等。** 平台在結算單上加前綴（`SP-`）、大小寫不一、
   混入全形字元。字串相等會把本來配得上的判成配不上。
2. **金額不會剛好相等。** 費率調整、運費補貼、部分退款都會讓兩邊差幾十元。
   把「編號對得上但金額差 40 元」當成完全不匹配，等於把最需要人看的那些
   案例丟進「查無此單」。
3. **有些列根本沒有編號。** 平台端的調整、補貼、跨期沖銷整欄留白。
   這些列如果丟掉，總額就永遠對不起來。

更根本的問題是：**單一規則只能輸出「配到／沒配到」，但下游需要的是「我有多確定」。**
一筆靠編號精確命中的可以直接入帳；一筆靠金額與日期猜出來的，任何人都不敢
不看就放行。把兩者混在同一個輸出裡，使用者只能全部重看一遍——
那就失去自動化的意義了。

## 決策

分三個階段，**階段本身就是信心水準的代理**。

| 階段 | 條件 | 下游可以怎麼處理 |
|---|---|---|
| Stage 1 精確 | 正規化後編號相符，且金額相符 | 自動放行，不需要人看 |
| Stage 2 容差 | 正規化後編號相符，金額有差 | 計算差額並歸因，人只要確認歸因對不對 |
| Stage 3 模糊 | 編號缺失或查無此單 | 候選集評分；過門檻才暫定匹配，一律進人工佇列 |

四個關鍵決定：

**一、正規化只用於比對，不改寫原始資料。**
`normalize_order_id` 做 NFKC → 去除不可見字元 → 轉大寫 → 去已知前綴 → 去非英數。
`Order.external_order_id` 保存平台實際印出來的字串——人工查核時必須看得到原文。
另外，正規化失敗時回傳 `None` 而不是 `""`：若都收斂成空字串，
所有缺編號的記錄會在 Stage 1 互相匹配上，產生大量假的對帳結果。

**二、自動化率只計 Stage 1。**
把 Stage 2 與 Stage 3 算進去，數字會從 79.6% 跳到 97%。但那兩種都必須有人確認過，
所以 97% 是自我欺騙。指標的定義必須對應「省下多少人力」，不是「配對率多高」。

**三、Stage 3 先縮小候選集再評分。**
用 `(平台, 金額分桶)` 建索引，每筆未匹配的結算列只跟同桶與相鄰桶的訂單比對。
桶寬必須**大於**金額容差——否則正確的候選會落在查詢範圍之外，
而且要查的桶數會隨容差增加，索引就失去意義。這個不變量寫在
`MatchingConfig.__post_init__` 裡，違反時直接拒絕建構。查詢固定看 −1／0／+1 三個桶。

評分是三個因素的加權和，權重相加必須為 1（同樣在 `__post_init__` 驗證）：

| 因素 | 權重 | 說明 |
|---|---:|---|
| 金額接近度 | 0.55 | 超出容差直接回 0，不進候選 |
| 日期合理性 | 0.15 | 落在撥款週期 (0, 45) 天之外直接回 0 |
| 商品名稱相似度 | 0.30 | `SequenceMatcher` 比值；**沒有名稱可比時給 0.5 不給 0** |

最後一項是刻意的：給 0 會把「資料不足」當成「證據不符」，那是兩回事。

**四、分數不夠就不猜，但要說出理由。**
低於門檻 0.82 時不硬配，而是列為漏記單並附上候選清單與可讀的理由
（「金額相差 80.00 TWD、訂單後 16 天結算、商品名稱相同」）。
理由不是裝飾——只給一個 0.54 的分數，沒有人敢按下確認。

## 考慮過的其他方案

**單一加權評分，不分階段。** 把編號相符也當成一個評分因素，全部走同一條路。
這樣程式碼更統一，但輸出就退化成一個分數，下游無法分辨
「編號完全相同」與「金額和日期剛好接近」——而這兩者的可信度差了一個數量級。
分階段的價值正是在保留這個區別。

**Stage 3 用匈牙利演算法求全域最佳解。** 這確實是正確的問題模型（指派問題），
目前用的是貪婪策略：每筆各自取最高分，一筆訂單只能被認領一次。
取捨的理由是分數夠高的配對通常也是唯一合理的配對，而分數不夠高的本來就要人工確認——
在這個情境下，全域最佳解改善的是那些「本來就要人看」的案例的排序，
效益有限而複雜度增加不少。**這是已知的簡化，不是疏忽**；
若日後實測誤配率偏高，這裡就是要改的地方。

**用 Levenshtein 距離比對訂單編號，取代正規化。** 編輯距離對「`SP-` 前綴」
這種系統性差異的處理其實比正規化差：前綴長度不同會讓距離變大，
但那明明是完全確定的對應關係。正規化把**已知的規則**寫成規則，
模糊比對只留給**真的不知道**的情況。

**降低 Stage 3 門檻來提高自動化率。** 這會直接讓數字變好看。但 Stage 3 的
錯誤是「把 A 訂單的錢算到 B 訂單頭上」，在對帳的情境下比漏掉一筆嚴重得多。
門檻定在 0.82 的理由是寧可多給人工看，不要製造假的勾稽。

## 後果

**好的：**

- 下游可以依階段決定處理方式，自動化率有了誠實的定義。
- Stage 2 的歸因把「金額不符」變成可行動的資訊（費率調整？運費補貼？退款？）。
- Stage 3 的候選理由讓人工確認從「重新對一次帳」變成「看三行字做判斷」。
- 所有可調參數集中在 `MatchingConfig` 並隨對帳結果一起記錄——
  「92% 的匹配率」在門檻 0.5 與 0.9 下是完全不同的兩件事。

**代價：**

- 三條路徑就是三份要維護的邏輯，而且它們共用去重與正規化的前處理。
- 評分權重與門檻目前是憑判斷定的，沒有用真實資料調校過（見下方限制）。
- `MatchResult` 必須支援「一筆訂單對應多列結算」，因為同一個編號常常
  同時出現銷售列與退款列。假設一對一會讓模型更簡單，但那正是
  真實對帳系統最容易出錯的地方。

**已知限制：**

- **索引帶來的是常數因子的改善，不是漸近改善。** 實測 n 從 250 到 2000 時，
  平均候選數 k 從 3.1 長到 14.2——因為商品價格範圍固定，訂單變多時
  每個金額桶就塞更多訂單。索引版約 O(n^1.6)、暴力版約 O(n^1.8)，
  兩條曲線平行往上。要讓 k 不隨 n 成長，桶寬必須隨資料密度縮小。
- 對照基準的定義是「進入 Stage 3 的列 × 尚未被前兩階段認領的訂單」。
  用「全部結算列 × 全部訂單」當分母會把倍數從 14 倍誇大到 200 倍以上——
  那是在跟一個沒有人會寫的爛實作比較。這個誇大在開發過程中真的發生過
  （前端自己乘出來的），修正的方式是把基準的定義收進領域層，
  讓前端、benchmark、文件都引用同一個數字。

## 驗證

不能只說「匹配率 79.6%」，必須證明那 79.6% 真的都配對正確。
`scripts/gen_fixtures.py` 在產生資料時把每一種刻意注入的狀況記錄進
`manifest.json`，`scripts/benchmark.py` 拿它逐項對答案：

```
✓ 正規化：編號被寫成小寫的訂單仍靠編號命中        9 / 9   （100.0%）
✓ Stage 3 召回率：訂單編號整欄空白的，靠模糊匹配救回  19 / 20  （95.0%）
✓ 分類：注入的金額差異被偵測到                  18 / 19  （94.7%）
✓ 守恆：沒有任何一筆訂單或結算列憑空消失         300/300、305/305
```

其中「守恆」是最重要的一條：對帳系統最危險的失敗不是配錯，是**憑空弄丟一筆**。
`tests/domain/test_properties.py` 另外用 Hypothesis 產生隨機輸入，
驗證資料守恆、不重複認領、金額一致、狀態合法四條不變量在任何輸入下都成立。

有一個判準本身曾經寫錯，值得記下來：最初「正規化有效」的檢查要求小寫編號
必須落在 Stage 1，結果有一筆同時被注入了退款，正當地降級到 Stage 2，
於是檢查失敗。**當時錯的是檢查，不是引擎**——真正代表正規化失效的訊號是落到
Stage 3。判準改成「Stage 1 或 2」，並在程式碼裡註明理由。
