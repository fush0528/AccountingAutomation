# ADR 0003：匯入的冪等性靠資料庫約束，不靠應用層檢查

- 狀態：已採用
- 日期：2026-09-17
- 相關：[ADR 0002](0002-three-stage-matching.md)（重複的列會直接污染對帳結果）

## 背景

上傳結算單是這個系統最容易被重複觸發的操作：

- 使用者按了兩次「上傳」
- 請求逾時，瀏覽器或反向代理自動重試
- 使用者重新整理頁面，表單重送
- 兩個分頁同時操作同一份檔案
- 平台自己重新匯出一份帳單，內容只多了一列新交易

前四種是同一份檔案進來兩次；第五種更麻煩——**整份檔案的內容不同，
但裡面大部分的列是重複的**。

重複匯入對對帳系統不是小問題。多出來的列會讓某筆訂單同時對應到兩列銷售，
金額翻倍，變成一個查不出原因的「金額差異」；或者被當成獨立的交易，
變成憑空多出來的「漏記單」。對帳報告的價值建立在「兩邊數字可以對得起來」，
一次重複匯入就能讓整份報告失去意義。

最直覺的寫法是先查再寫：

```python
if not session.query(Batch).filter_by(content_hash=h).first():
    session.add(Batch(content_hash=h, ...))     # ← 這裡有問題
```

這在單執行緒的手動測試裡永遠會過，但它**在併發下是錯的**：
兩個請求可以同時查到「沒有」，然後雙雙寫入。查詢與寫入之間存在一個窗口，
應用層無法把它關掉。

## 決策

三道互相獨立的防線，每一道擋不同的東西。

| 防線 | 機制 | 擋得住什麼 |
|---|---|---|
| 1 | 檔案內容 SHA-256 ＋ 唯一約束 | 同一份檔案再上傳（改檔名也沒用） |
| 2 | 每列 fingerprint ＋ 唯一約束 | 檔案改過，但裡面的列重複 |
| 3 | 整批包在單一交易 | 中途失敗留下半批資料 |

**核心原則：唯一約束是資料庫保證的真正不變量，應用層要做的是處理被拒絕的情況，
而不是試圖預先避免它。** 所以流程是「先嘗試寫入，再捕捉 `IntegrityError`」，
不是「先查詢，沒有才寫」。這在分散式系統裡叫**至少一次投遞下的恰好一次語意**：
呼叫端可以放心重試，結果不會變。

三個實作細節值得說明：

**一、指紋算的是檔案內容，不是檔名。**
`content_hash` 是整份檔案位元組的 SHA-256。改檔名重傳會被擋下，
這正是我們要的——檔名不是身分。

**二、列指紋排除 `source_row`，並把 `None` 明確編碼。**
`row_fingerprint` 取平台、訂單編號、結算日、三個金額、記錄類型算雜湊。
不含列號：同一筆交易在不同檔案裡的列號當然不同，把它算進去就等於沒有去重。
而 `None` 必須編成一個具體字串（`"\x00NULL"`），因為 **SQL 的 NULL 彼此不相等**——
直接對欄位下複合唯一約束的話，兩列都沒有訂單編號時會雙雙插入成功。
這也是選擇「算一個雜湊欄位下唯一約束」而不是「多欄位複合唯一約束」的原因。

**三、列的去重用一次批次查詢，不是逐列 try/except。**
逐列捕捉 `IntegrityError` 在 PostgreSQL 上會讓整個交易進入 aborted 狀態，
後續所有語句都會失敗。所以先把這批的所有指紋一次查出來，在記憶體裡過濾，
再整批寫入。唯一約束仍然在，它是併發下的最後防線；批次查詢只是讓
單一請求內的常見情況不必依賴例外處理。

**四、`was_duplicate` 是回傳型別的一部分。**
「匯入成功，寫了 305 列」與「這份檔案先前已匯入過，回傳原批次」都是成功，
但意義完全不同。呼叫端必須能分辨，所以這不是一段訊息文字，是一個布林欄位。
同理，`ImportFailed` 帶 `code`，讓前端能分辨「認不出平台」（可以手動指定重試）
與「格式不符」（重試也沒用）——只給中文訊息的話，前端只能比對字串來決定行為。

## 前端刻意不做防連擊

一般做法是上傳中把按鈕 disable。這裡**故意不做**，理由是它擋不住真正的重複：
網路逾時後的自動重試、使用者重新整理、兩個分頁同時操作，前端全都攔不到。
做了防連擊只會讓人以為問題解決了。

所以反過來：讓使用者可以重複傳，然後把 `was_duplicate` 明確顯示出來。
**重複上傳不是要被阻止的錯誤，是一個正常且安全的結果。**
上傳頁的說明文字直接寫著「試試看把同一份傳兩次」——這是把正確性做成可以示範的東西。

## 考慮過的其他方案

**由呼叫端帶 idempotency key。** 這是支付 API 的標準做法（Stripe 等），
可靠而且語意清楚。但它要求呼叫端正確地產生與重用 key——在這個情境下
「呼叫端」是使用者手動拖檔案的瀏覽器，沒有天然的 key 可用。
檔案內容的雜湊本身就是最自然的 idempotency key，而且不需要呼叫端配合。

**在應用層加鎖（如 Redis 分散式鎖）。** 多一個必須運維的元件，
而且鎖失效、鎖逾時、持鎖者當掉這些問題都要處理。
唯一約束不需要額外元件，而且它的保證比鎖更強——就算應用層完全沒有防護，
資料庫也不會接受重複。

**用 `INSERT ... ON CONFLICT DO NOTHING`。** 語意正確而且高效，
但那是 PostgreSQL／SQLite 的方言。本專案的一條硬規則是不寫原生 SQL、
不用資料庫特有功能，才能保證 SQLite 與 PostgreSQL 行為一致
（見 [ADR 0004](0004-layering-and-dependency-inversion.md)）。
批次查詢 ＋ 唯一約束是可攜的等價做法。

## 後果

**好的：**

- 呼叫端可以無腦重試，這讓前端與網路層的設計都變簡單。
- 併發安全不靠時序運氣，靠資料庫的不變量。
- 「平台重新匯出、只多一列」這個很實際的情境被第二道防線正確處理：
  實測結果是 `accepted_count: 1, skipped_duplicate_rows: 4`。

**代價：**

- 每列多存一個 64 字元的雜湊欄位與一個唯一索引，寫入略慢、空間略大。
- 列指紋把整列內容編進去，所以**合法的重複列也會被擋下**。
  例如同一天同一筆訂單真的有兩筆金額完全相同的退款——目前無法表示。
  真要支援，指紋必須納入平台端的交易流水號（部分平台有，部分沒有）。
  這是已知限制，不是疏忽。
- 三道防線分散在服務層與資料表定義兩處，讀程式的人要看兩個地方才看得全。
  緩解方式是在 `import_service.py` 的模組 docstring 把三道一起說明。

## 驗證

`tests/api/test_api.py::TestIdempotency` 有六個測試守著這件事，包括：

- 同一份檔案傳兩次 → 第二次 `was_duplicate: true`，資料庫列數不變
- 連續傳五次 = 傳一次
- **檔案改過但列重複** → `was_duplicate: false`（確實是不同檔案）
  但 `accepted_count: 1, skipped_duplicate_rows: 4`

第三個是最重要的一條，因為它是唯一能證明第二道防線存在的測試——
只有第一道的話，那個案例會整批重複寫入。

這些測試在記憶體 SQLite 與真實 PostgreSQL 16 上都跑過同一份，
確保行為不是靠某個資料庫的特定實作細節成立的。
