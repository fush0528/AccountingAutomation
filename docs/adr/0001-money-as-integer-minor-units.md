# ADR 0001：金額以最小貨幣單位的整數表示

- 狀態：已採用
- 日期：2026-09-08
- 取代：v1（`legacy/`）以 `float` 儲存金額的做法

## 背景

第一版的 `AccountingEntry` 以 `float` 儲存銷售總額、平台手續費與實收金額：

```python
@dataclass
class AccountingEntry:
    total_sales: float
    platform_fee: float
    actual_income: float = 0.0

    def calculate_actual_income(self) -> float:
        return self.total_sales - self.platform_fee
```

在單筆記帳的情境下這沒有明顯問題。但當系統要對一整個月的訂單做總額比對時，
累加誤差就會浮現：實收金額的合計與平台結算單的撥款金額出現無法解釋的尾差，
而且金額愈多筆、差距愈大。

根本原因是 IEEE 754 二進位浮點數無法精確表示 0.1、0.01 這類十進位小數：

```python
>>> 0.1 + 0.2 == 0.3
False
>>> sum(0.1 for _ in range(1000))
99.9999999999986
```

對帳系統的整個價值建立在「兩邊金額是否相等」這個判斷上。
一個連相等性都不可靠的數值型別，不能作為它的基礎。

## 決策

金額改用值物件 `Money`，內部以**最小貨幣單位的整數**儲存
（TWD 的最小單位是分，1 元 = 100）。

1. 加減法在整數上進行，永遠精確。
2. 乘法只接受 `int` 或 `Decimal`；傳入 `float` 會拋出帶說明的例外。
3. 捨入策略明確指定為 `ROUND_HALF_UP`（財務慣例的四捨五入），
   而不是 Python `Decimal` 預設的 `ROUND_HALF_EVEN`（銀行家捨入）。
4. 不提供 `from_float()`。把浮點數轉成金額沒有安全的預設行為，
   呼叫端必須自己決定捨入方式，再透過 `from_decimal()` 傳入。
5. 分攤（`allocate`）採 largest remainder method，保證分攤後總和等於原金額。

## 考慮過的其他方案

**直接用 `decimal.Decimal`。** 精度沒問題，是很合理的選擇。但 `Decimal` 本身
不帶幣別，也擋不住 `Decimal("100") + Decimal("100")` 這種跨幣別相加；
而且它允許無限位數，中間計算會累積出 `100.00000000000001` 這種需要
額外 quantize 才能收斂的值。`Money` 內部仍然用 `Decimal` 做解析與捨入，
但把「什麼時候捨入到多少位」這個決定收在型別裡，而不是散落在呼叫端。

**用整數存「元」，捨棄小數。** TWD 日常交易確實以元為單位。但平台手續費是
費率乘售價（例如 5.53%），中間結果必然有小數。提早捨入會讓誤差進入
每一筆資料，而不是只在最後顯示時發生一次。

**在資料庫層用 `NUMERIC` 就好，程式裡照用 float。** 這只是把問題推遲到
Python 這一側，中間運算仍然不精確。

## 後果

**好的：**

- 金額相等性可靠，對帳的核心判斷有了正確的基礎。
- 幣別混用在型別層被擋下（`CurrencyMismatchError`），不會靜默算出錯的數字。
- 分攤不會產生尾差，`allocate` 的測試直接驗證這件事。
- 領域層可以在沒有資料庫的情況下完整測試。

**代價：**

- 所有金額都要經過建構子，parser 不能直接把欄位值塞進模型。
  這其實是好事——它強迫解析錯誤在邊界就被發現。
- 直接建構 `Money(12345)` 傳的是分而不是元，容易誤用。
  緩解方式是日常一律使用 `Money.from_str()`，並在 docstring 標明。
- 與外部系統交換資料時要明確決定序列化格式（本專案採字串，不用浮點數）。

## 驗證

`tests/domain/test_money.py::TestFloatIsWrong` 把這個問題釘成可執行的測試：
它同時證明 float 會漂移、而 `Money` 不會。這組測試的用途不是防止回歸，
而是讓「為什麼要改」變成程式碼的一部分，而不是 README 裡的一句宣稱。
