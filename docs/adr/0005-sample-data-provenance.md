# ADR 0005：測試資料是合成的，欄位規格取自公開文件

- 狀態：已採用
- 日期：2026-09-17

## 背景

本專案沒有真實的結算單。作者不是任何電商平台或金流商的商家，
拿不到真實的對帳檔，也不應該把別人的交易資料放進公開的 repo。

但「沒有真實資料」有兩種做法，差別很大：

1. **憑印象編欄位。** 想像對帳單長什麼樣子，自己編一組欄位名。
   問題是編出來的東西會剛好符合自己想寫的程式——解析器處理的
   困難都是自己設計的困難，等於在解一個假問題。
2. **欄位規格照公開文件，資料本身是合成的。** 欄位名稱、日期格式、
   編碼選項、金額寫法都有出處；只有金額與編號是產生的。

本專案採第 2 種。

## 決定

三個平台各自對應現實中一種**不同來源**的對帳檔，而不是三個長得差不多
的假平台。這一點比「支援三種格式」重要——真正的困難不是副檔名不同，
是同一件商業事實有三種描述方式。

| | 現實中的來源 | 格式 | 規格出處 |
|---|---|---|---|
| 平台 A | 第三方金流商的撥款對帳檔 | UTF-8／Big5 CSV | 綠界科技（ECPay）公開技術文件，見下 |
| 平台 B | 電商平台賣家後台匯出的報表 | Excel | 依一般賣家後台報表的共同結構設計 |
| 平台 C | 舊 ERP／供應商對帳單 | Big5 CSV、民國年 | 依台灣本地系統的常見慣例設計 |

### 平台 A：有明確出處

欄位取自綠界科技公開的「下載撥款對帳檔」與「下載對帳檔 V2」規格：

- <https://developers.ecpay.com.tw/?p=16415>（撥款對帳檔）
- <https://developers.ecpay.com.tw/?p=2896>（對帳檔 V2）

從中採用的三個特徵，都是憑空想像不會想到的：

1. **手續費拆成多個科目。** 撥款對帳檔同時有「金流手續費」「平台手續費」
   「金流處理費」。對金流商是不同的成本科目，對「這筆訂單被扣多少」
   是同一件事——所以 parser 要相加，領域模型只留一個 `fee_amount`。
2. **退款是銷售列上的欄位，不另起一列。** 平台 C 的退貨是獨立的一列。
   同一個商業事實、兩種表示法，這是 parser 抽象真正要吸收的差異。
3. **編碼是下載時的參數。** 文件寫明「若為 Big5 格式時，則參數請帶 1；
   若為 UTF8 格式時，則參數請帶 2」。所以同一個平台的同一份報表，
   兩種編碼都可能出現——parser 兩種都必須能讀，不能靠副檔名或平台猜。

為了避免這份合成資料被誤認為真實的金流對帳檔，**欄位名稱中所有指涉特定
公司的字樣都改成通用詞**（「特店交易編號」→「廠商訂單編號」、
「綠界交易編號」→「金流交易編號」）。規格的結構保留，品牌不保留。

### 資料本身

所有金額、訂單編號、商品名稱、日期都由 `scripts/gen_fixtures.py` 與
`scripts/gen_samples.py` 產生，固定種子、可重現。**沒有任何一筆來自
真實交易。** 這件事在 README、`SAMPLES.md` 與兩支產生器的 docstring
都寫明，不做任何有真實資料的暗示。

## 後果

**好的：**

- 「欄位結構參考公開的結算單格式」這句話變成可查證的，有連結可點。
- 多了兩個不是自己發明的解析難點（多科目費用、同列退款），
  而這兩個正好逼出 parser 抽象真正的價值。
- 平台 A 的對帳檔自帶「應收款項(淨額)」欄位，可以拿來**交叉驗證**
  我們自己的解讀。實作見 `PlatformAParser._cross_check`——
  對不上就讓該列失敗，而不是產生一筆少扣費用、看起來正常的記錄。

**要承認的限制：**

- 平台 B 與平台 C 沒有同等級的公開規格出處。它們的欄位是依常見結構設計的，
  代表性不如平台 A。
- 就算欄位規格有出處，**資料分佈仍然是猜的**。各種狀況的注入比例
  （空白編號 6%、金額差異 7%、部分退款 4%⋯）沒有真實依據。
  所以 benchmark 得到的 79.6% 自動化率，正確的讀法是
  「在這個假設的資料分佈下，引擎的行為符合 ground truth」，
  **不是**「本系統在真實環境可達 79.6%」。這個區別在 README 也寫明了。
- 拿到真實資料時最可能先壞掉的地方：本模型假設一份對帳檔只有一種幣別、
  費用科目最多三項，而且每一列都對應得到某一筆訂單或某一個平台調整。
  真實的對帳檔還會有跨期沖銷、廣告費扣款、保證金這類與單筆訂單無關的列。

## 替代方案

**用公開資料集。** 找過，沒有公開的台灣電商平台結算單資料集——
這類資料本質上是商業機密。

**直接用真實規格的欄位名稱（含公司名）。** 出處更明顯，但一份內容全是
假資料、欄位卻標著特定公司名的檔案，容易被誤認為真的來自該公司。
不值得為了一點點說服力承擔這個誤解。
